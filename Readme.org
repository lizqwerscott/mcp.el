This is an Emacs client for interfacing with [[https://modelcontextprotocol.io/introduction][MCP]], supporting connections to MCP servers.

* Features
- Structured communication with MCP servers
- Support for filesystem and generic MCP servers
- Extensible tool and prompt system
- Asynchronous and synchronous operations
- Resource management capabilities
- Intuitive interface for managing server lifecycle (start/stop/restart)
- Integration with popular Emacs packages (e.g., gptel, llm)

*** Establish the connection first.
#+begin_src elisp
  (mcp-connect-server "filesystem" 
                      :command "npx" 
                      :args '("-y" "@modelcontextprotocol/server-filesystem")
                      :roots '("~/Downloads/" "~/Documents/")
                      :initial-callback
                      #'(lambda (connection)
                          (message "%s connection" (jsonrpc-name connection)))
                      :tools-callback
                      #'(lambda (connection tools)
                          (message "%s tools: %s" (jsonrpc-name connection) tools))
                      :prompts-callback
                      #'(lambda (connection prompts)
                          (message "%s prompts: %s" (jsonrpc-name connection) prompts))
                      :resources-callback
                      #'(lambda (connection resources)
                          (message "%s resources: %s" (jsonrpc-name connection) resources)))
#+end_src
*** Using Roots with Filesystem Server
The filesystem server uses the MCP roots protocol to determine which directories it can access. Instead of passing directories as command-line arguments, you can specify them using the =:roots= parameter:

#+begin_src elisp
  (mcp-connect-server "filesystem" 
                      :command "npx" 
                      :args '("-y" "@modelcontextprotocol/server-filesystem")
                      :roots '("/home/user/project1" "/home/user/project2"))
#+end_src

You can also dynamically manage roots after the server is connected:

#+begin_src elisp
  ;; Add a new root directory
  (mcp-add-root "filesystem" "/home/user/new-project")

  ;; Remove a root directory
  (mcp-remove-root "filesystem" "/home/user/old-project")

  ;; Replace all roots
  (mcp-set-roots "filesystem" '("/home/user/project1" "/home/user/project2"))

  ;; View current roots
  (mcp-get-roots "filesystem")
#+end_src

Roots can also be specified as plists with additional metadata:
#+begin_src elisp
  (mcp-connect-server "filesystem"
                      :command "npx"
                      :args '("-y" "@modelcontextprotocol/server-filesystem")
                      :roots '((:uri "file:///home/user/project" :name "My Project")
                               "/home/user/downloads"))
#+end_src
*** Define the use of tools.
The current text is being tested using the [[https://github.com/karthink/gptel/issues/514][gptel tool]] branch.Use =mcp-make-text-tool= to create standard tool call data ([[https://github.com/ahyatt/llm/discussions/124][Discussions]]).It is recommended to create tools within the tools-callback or wait for the mcp connect server to complete.
#+begin_src elisp
  (mcp-make-text-tool "filesystem" "write_file")
#+end_src
This will generate a data structure where the function is an auto-generated synchronous or asynchronous lambda function for accessing the MCP server.
#+begin_src elisp
  (list :function #'(lambda (&rest args)
                      ;; Synchronous or asynchronous access to the MCP server's Lambda function.
                      )
        :name "write_file"
        :async nil
        :description "Create a new file or completely overwrite an existing file with new content. Use with caution as it will overwrite existing files without warning. Handles text content with proper encoding. Only works within allowed directories."
        :args ((:type "string" :name "path" :description "path")
               (:type "string" :name "content" :description "content"))
        :category "files")
#+end_src

*** Manual function call
**** Synchronize
#+begin_src elisp
  (let ((connection (gethash "filesystem" mcp-server-connections)))
    (mcp-call-tool connection "write_file" '(:path "filename or file path" :content "the file content")))
#+end_src
**** Asynchronous
#+begin_src elisp
  (let ((connection (gethash "filesystem" mcp-server-connections)))
    (mcp-async-call-tool connection
                         "write_file"
                         '(:path "filename or file path" :content "the file content")
                         #'(lambda (res)
                             ;; handle res
                             (mcp--parse-tool-call-result res))
                         #'(lambda (code message)
                             ;; handle error
                             (format "call %s tool error with %s: %s"
                                     tool-name
                                     code
                                     message))))
#+end_src

* OAuth for remote Streamable HTTP servers

=mcp.el= 0.2 adds native OAuth 2.1 authorization-code support for remote
Streamable HTTP MCP servers.  It discovers protected-resource and authorization
server metadata, registers a public client when required, uses S256 PKCE with a
localhost loopback redirect, sends RFC 8707 resource indicators, refreshes
tokens before they expire, and retries an unauthorized POST once after
authorization.

#+begin_src elisp
  (mcp-connect-server
   "remote"
   :url "https://mcp.example.com/mcp"
   :oauth '(:client-name "Emacs MCP"
            :scopes ("tools:read")
            :redirect-uri "http://localhost:49152/mcp/oauth/callback"
            :open-browser t))
#+end_src

=:oauth= accepts an =mcp-oauth-provider= or a configuration plist.  Supported
keys are =:client-name=, =:scopes=, =:metadata-url=,
=:authorization-server=, =:static-client=, =:storage-directory=,
=:open-browser=, =:allow-http=, =:redirect-uri= and =:grant-type=.  The
registered =:redirect-uri= must be an exact =http://localhost:PORT/PATH= URL;
it is used for the default authorization-code S256 PKCE flow.  HTTPS is
required for MCP and discovered OAuth endpoints unless the explicit
development-only =:allow-http= option is
non-nil.  The client validates resource and issuer before reusing state.  It
first tries the RFC 9728 path-derived metadata URL; when that fails, it makes
one unauthenticated MCP initialize probe and follows only a 401 Bearer
=resource_metadata= challenge.  Set =:metadata-url= to explicitly override
this discovery (the override is always used directly).

=:transport= selects the URL transport: =auto= keeps the existing legacy SSE
behavior for unauthenticated URLs, =sse= explicitly requests that behavior,
and =streamable= selects Streamable HTTP.  OAuth always selects Streamable
HTTP.  OAuth requests never follow redirects, so a 3xx response cannot carry
tokens, device codes, or client data across an origin boundary.

OAuth state is stored atomically under =~/.emacs.d/mcp-oauth/= by default;
its directory is mode 0700 and its state files are mode 0600.  State contains
client registration and refresh credentials.  It is never written to Custom,
process arguments, messages, or the event log.  On =invalid_grant=, stale state
is removed and the next request begins authorization again.

The first authorization opens its PKCE authorization URL when =:open-browser=
is non-nil and waits for the registered loopback callback.  This implementation
supports public clients only: static and dynamically registered clients must use
=token_endpoint_auth_method= =none= (or omit it).  RFC 8628 device authorization
is retained only as an explicit non-standard extension: set =:grant-type= to
=device-code=, and configure a server registration which supports that grant.
Discovery and token exchanges are synchronous only on the cold/expired-token
path; valid tokens use cached metadata and do not block on discovery.  On
POSIX, PKCE randomness comes from =/dev/urandom=; native Windows uses the
built-in PowerShell/.NET cryptographic RNG and fails closed if unavailable.
Existing users of =mcp-remote= can remove its stdio bridge and configure the
remote URL plus =:oauth= directly once their server supports standard metadata
and authorization-code endpoints.
